# 촬영본 + 화면녹화 2소스 리컷

캠(토킹헤드)과 화면녹화를 따로 돌린 스크린캐스트를 한 편으로 묶는 절차.
0827 겜쫀쿠(캠 15:38 + 화면 15:20 → 8:22)에서 확립했다. 전부 실측이다.

이 문서는 **2단계(에이전트 가편집)** 의 기술 상세다. 사용자와 주고받는 4단계 전체 흐름은
`SKILL.md` 의 "사용자와 4단계로 주고받는다" 를 본다.

## 1. 싱크는 오디오로 잰다

**파일명·`creation_time` 을 믿지 마라.** 초 단위라 프레임 정확도가 안 나온다.
두 녹화가 같은 목소리를 담고 있으면 오디오 상호상관이 정답을 준다.

```bash
python3 scripts/sync-offset.py <캠> <화면녹화>
```

10ms 포락선 FFT 상관으로 대략을 잡고, 원시 파형으로 10지점에서 재측정한다.
**같은 오디오 클럭이면 900초에 걸쳐 드리프트가 0ms 다** (0827 실측: 오프셋 8.41472s,
표준편차 0.05ms, 드리프트 -0.1ms). 표준편차가 5ms 를 넘으면 클럭이 다른 것이고
리샘플을 검토해야 한다.

상호상관은 디코딩 오디오 배열 기준이다. **양쪽 컨테이너의 audio start_time 차이를 더해**
영상 배치 시각으로 환산한다(video start_time 도 함께 확인). 부호·환산 예는 `pitfalls.md` 의
`sync-offset.py` 항목. 적용 후 양쪽 오디오를 여러 지점에서 다시 대조한다. CapCut 이 열면서
1.809151 → 1.833333s 로 스냅한 것은 24ms 로 30fps 의 1프레임 미만이라 정상(1021).

## 2. 컷은 한쪽 프레임 인덱스로 잡고 양쪽에 같이 먹인다

캠을 기준 타임라인으로 삼는다(자막·오디오가 거기 붙어 있다).

- 컷 구간은 **캠 프레임 인덱스**로 정의한다. 초 단위로 반올림하면 세그먼트마다
  1µs 씩 어긋나 누적된다.
- 화면녹화는 `-itsoffset <OFF>` 로 캠 시각에 얹은 뒤 **같은 select 식**을 먹인다.
  `-ss` 를 `-i` 앞에 두면 반대 방향으로 당겨져 2×OFF 만큼 어긋난다.
- `fps=30` 을 select 앞에 둬서 두 소스의 프레임 수가 정확히 같아지게 한다.

```bash
ffmpeg -itsoffset 8.414725 -i screen.mov \
  -filter_complex "[0:v]fps=30,select='<캠 기준 식>',setpts=N/30/TB,scale=…[v]" …
```

**검증**: 완성본 오디오 ↔ 같은 컷을 먹인 **화면녹화 쪽 오디오**의 상호상관 lag 이
구간별로 0ms 부근이며 누적 드리프트가 없어야 한다. ffmpeg 합성의 상수 오차는
`pitfalls.md` 의 start_time 보정을 확인한다. draft 는 앱의 1프레임 미만 스냅을 구분해 보고한다.

## 3. 무음편집 — threshold 를 먼저 고른다

`capcut-silence-editing` 이 참조하는 `docs/agent-rules/audio-breath-aware-silence-editing.md`
§3.1.1 표적 2차 패스를 쓴다. 다만
**기본값 `-28dB` 를 그냥 쓰지 마라.**

auto-editor 의 dB 는 **파일 피크 상대값**이다. 저레벨 직녹음(피크 -8dBFS 급)에서는
`-28dB` 의 실효 임계가 발화 대역 한복판에 떨어진다.

0827 실측 (파일 피크 -8.09 dBFS, 30ms RMS p70~p99 = -35~-26 dBFS):

| threshold | 실효 dBFS | 삭제 구간 | 발화급 피크 포함 |
| ---: | ---: | ---: | ---: |
| -28dB | -36.1 | 458 | **223 (49%)** |
| -35dB | -43.1 | 308 | 27 (9%) |
| -40dB | -48.1 | 266 | 6 (2%) |
| -45dB | -53.1 | 265 | 1 (0.4%) |

**고르는 법**: ① 30ms RMS 백분위로 노이즈 플로어·발화 레벨을 본다 ② threshold 후보마다
**현재 기준선 대비 추가 삭제 구간의 30ms 음성대역 RMS 최대값**을 전수 측정한다 ③ 그 값이 발화 본체(p70)보다 확실히
아래인 가장 높은 threshold 를 고른다.

> ⚠ **게이트를 peak 로 잡으면 안 된다.** 숨소리·입소리·클릭 같은 고립 트랜지언트가
> 그대로 걸려서 "발화가 들었다" 고 오판하게 만든다. 0905 실측: 한 구간이 피크 -35.3 dBFS 로
> 걸렸지만 14,880샘플 중 **3개(0.02%)** 만 -40dBFS 를 넘었고 30ms RMS 는 최대 -58.3 dBFS 였다.
> 지워야 할 잡음이지 발화가 아니다.
>
> **이 오판의 대가가 크다.** 그 게이트를 믿고 0905 를 피크대비 **-48.8dB**(-68 dBFS)까지 내렸는데,
> 노이즈 플로어가 -77 dBFS 라 디지털 무음만 잡히고 **말 사이 룸톤(-45~-55 dBFS)이 전부 살아남았다.**
> 사용자가 "무음편집이 적용 안 되었다" 고 했다. RMS 게이트로 다시 재니 -54 dBFS(피크대비
> **-34.8dB**)까지 안전했고 — 0819·0827 이 확립한 **-35dB** 과 같은 자리다 — 제거량이
> 68.3s → **117.0s** 로 늘었다.
>
> **위 -35dB 수렴은 0819·0827·0905의 과거 실측이지 기본값이 아니다**(2026-10-22 대체).
> 1021은 피크 −4.5dBFS·발화 대역 RMS −45~−32로, -28dB 적용 시 34:36 → 9:25,
> -35dB 단독도 9:34를 더 잘랐다. 숫자를 재사용하지 말고 위 전수 측정으로 고른다.

패스는 나눠서 조인다. 매번 **현재 draft 를 기준선으로 고정**하고 `기준선 - 확정 컷` 만
만든다. 전체 threshold 로 갈아엎지 않는다.

아래는 0827의 과거 패스 기록이며 다음 영상의 프리셋이 아니다.

| 패스 | threshold | MIN_GAP | 컷 | 제거 |
| --- | --- | --- | ---: | ---: |
| 2 | -45dB | 0.24s | 147 | 67.1s |
| 3 | -40dB | 0.18s | 103 | 25.0s |
| 4 | -35dB | 0.16s | 123 | 26.2s |

**"숨소리·답답함 제거 / 더 강하게"는 임계 강화가 아니다.** 사용자: "너무 강하게 라고 해버리면 분량이 다 날아가잖아".
공백 컷은 **auto-editor 공백 ∩ Silero VAD 비발화 ∩ 남길 어절∩소리 밖**만 허용한다.
0.3s+ 컷은 하나씩 재전사해 실제 단어가 나오면 거부한다(레벨·VAD로 확인한 무음의
`감사합니다`·`한글자막 by…` 환각은 통과). 쉼은 ≥0.2s 남기고 조작 중 공백에는 §4 모션 가드를 더한다.
주기성·centroid 같은 숨소리 특성만으로 클립 내부를 자르지 않는다(1021 후보 절반이 실제 단어).
상세 게이트는 `docs/agent-rules/capcut-draft-editing-workflow.md` §3.3을 따른다.

## 4. 스크린캐스트에는 화면 모션 가드가 필요하다

오디오 규칙만 돌리면 **조작 장면(페이지 로딩·클릭·타이핑)을 무음이라고 통째로 지운다.**
0827 2패스 후보 109.7초 중 **52.1초가 화면이 움직이는 순간**이었다.

화면녹화를 2Hz 로 다운스케일해 프레임차를 재고(`fps=2,scale=192:124,format=gray`),
`>0.5` 인 프레임 비율로 gap 을 분류한다.

- `busy > 0.15` (조작) — 시작 0.7s + 결과 1.1s 는 남기고 가운데만 자른다
- `busy > 0.05` — 0.4s + 0.6s
- 그 외(정지) — §3 교집합을 통과한 부분만, 쉼 ≥0.2s 보존

위 busy·패딩 수치는 0827·0905 기록이다. 1021 표적 패스는 조작 공백 최대 0.8s 유지(상세 지침 §3.3).
모션 가드가 있다는 이유로 조작·메뉴가 필요한 프레임을 통째로 버리지 않는다.

**이건 오디오 게이트를 완화하는 게 아니라 그 위에 얹는 별도 가드다.**

> ⚠ **패딩에 상한을 둬라.** `0.7 + 1.1 = 1.8s` 는 gap 이 몇 초일 때의 값이다. 0.3~0.9s gap 에
> 그대로 적용하면 남는 컷이 **음수**가 되어 컷이 통째로 버려진다 — 0905 실측: VS Code 구간
> 후보 28개 중 **15개가 그렇게 사라져** 약 15초의 무음이 남았고, 사용자가
> "무음편집이 안 된다" 고 했다. `pad ≤ gap × 0.35` 와 `유지 총량 ≤ 1.2s` 를 같이 건다.

> ⚠ **cue 를 재계획의 입력으로 쓰지 마라.** 자막 cue 는 **이미 잘린 타임라인** 기준이다.
> 그걸 캠으로 되돌려 전체를 다시 계획하면 옛 컷 자리마다 패딩을 돌려주게 되어 길이가
> **되레 늘어난다**(0905 실측 5:27 → 5:56). 자막이 생긴 뒤의 보정은 **현재 keeps 를 기준선으로
> 두는 표적 패스**여야 한다.

## 5. 버벅임은 자막만 고치면 안 된다

`audio-breath-aware-silence-editing.md` 의 실패 조건이다 —
"반복 발화의 앞 자막만 숨기고 오디오는 남겼다".

퇴고에서 `작업을 작업이 → 작업이` 처럼 텍스트를 고쳤으면 **오디오도 잘라야** 한다.
**자막 전체를 사람이 읽고 실패 발화를 어절 인덱스로 표시**한다. 원본 `words` 의 문자 비례
보간은 후보 시각일 뿐이다. 읽기속도 >13자/초처럼 시각이 눌린 cue 는 에너지 골짜기 후보마다
그 지점부터 잘라 whisper 로 전사해 경계를 실측한다. 경계는 남길 어절 밖으로만 잡는다.
**적용 전 컷을 반영한 미리보기를 재전사하고 모든 join 앞뒤 문장을 읽는다.**
군말(어/음/아/응)도 오디오에서 제거한다. 자막에서만 지우면 실패다.
즉흥 강의의 대본은 용어·표기 근거로만 쓰며 대본 구조대로 내용을 잘라내지 않는다.

**주의** — 리세그멘테이션을 하면 `words` 가 비워진다. 원본 draft 백업에서 읽어야 한다.
그리고 다음은 버벅임이 아니다:

- `이 이벤트`·`그 스킬` — 지시관형사. 지침상 보존
- `1개월 3개월 6개월` — 열거. 반복이 아니다
- `겜스고 겜쫀쿠` — 다른 낱말

## 5b. 자막이 없어도 실패 발화는 잘라야 한다 (0905)

§5 는 CapCut 자동자막의 `words` 가 있다는 전제다. **자막을 안 만든 소스에서 "판정 근거가
없다" 며 건너뛰면 안 된다.** 카드 카피를 위해 어차피 STT 를 돌리므로(파이프라인 A+B) 그
단어 타임코드는 후보 근거다. §5 경계 실측·미리보기 재전사를 거쳐야 한다. 지침의 요구는 그대로다 —
**앞 실패 발화를 오디오에서 지우고 뒤 성공 발화를 살린다.**

### 절차

1. **후보 뽑기** — 22초 창 안에서 2~5어절이 반복되면 후보. 긴 n-gram 우선, 겹치면 병합.
2. **하나씩 읽고 판정한다.** 0905 실측: 자동 검출 **18건 중 10건만** 실패 발화였다.
   버린 8건은 전부 자연스러운 반복이다 —
   병렬 구조(`A를 볼 수가 있고 B를 볼 수가 있고`), 연속 문장(`이런 것들을 …. 이런 것들을 …`),
   흔한 어구가 10초 이상 떨어져 재등장(`응대를 해야`·`것 같아요`).
   **알고리즘에 판정을 맡기지 마라.**
3. **경계는 어절 사이 빈틈 안에서만 움직인다.** ±고정 radius 로 RMS 최소점을 찾으면
   이웃 어절을 넘어가 말을 잘라먹는다 — 0905 실측 **10건 중 3건**이 깨졌다
   (`물론 물론` 중복 · `서버에서는` 소실 · `질문을 [해보시면서]` 소실).
   경계 시각이 걸친 두 어절의 `[앞말 end, 뒷말 start]` 구간 **안에서만** 최소점을 찾는다.
   (0827 이 "자막 큐 경계에 스냅" 한 것과 같은 원리다 — 단위 경계 밖으로 나가지 않는다.)
4. **자르기 전에 컷 후 텍스트를 재구성해 읽는다.** 앞뒤 6~7어절을 이어 붙여
   문장이 성립하는지 본다. 위 3건은 전부 이 단계에서 잡혔다.
5. 실패 발화 제거는 **발화 피크 게이트를 걸지 않는다** — 자를 구간이 곧 발화다.
   무음컷의 `-18dB` 게이트를 여기 적용하면 아무것도 못 자른다.

> ⚠ **whisper 루프 아티팩트를 재발화로 오인하지 마라.** large-v3 는 긴 파일에서 한 문장을
> 수십 번 반복 출력한다. 0905 원본 전사는 3:36 부터 `이제 잠깐 포맷을 보시면…` 을 4번 뱉었는데
> 실제 오디오에는 한 번뿐이다. **청크 재전사본과 대조해 루프를 걷어낸 전사로 후보를 뽑는다.**
> 판별: 청크본에서 한 번만 나오면 아티팩트를 의심한다. 양쪽 다 반복이어도 실제 오디오와
> 앞뒤 문장을 확인한 뒤 재발화로 확정한다.

### 0905 결과

컷 10건 · 출력 **394.5s → 359.6s (5:59.6)**. 종류는 셋이다 —
말을 하다 끊고 다시 시작(`그래서 자연스럽게 자동 응대봇 이거를 구축하게` → 다시),
같은 문장 중복(`직원들보다 훨씬 잘하는 것 같습니다` / `…같아요`),
어절 더듬음(`클로드한테 클로드한테` · `목적별로 여러가지` ×2).

**카드 시각은 remap 한다.** 타임라인이 줄면 카드가 밀린다. 카피는 그대로 두고 시각만
새 keeps 로 투영해 `card-windows-remap.json` 을 만들고 그래픽을 다시 렌더한다.

## 5c. 사용자 자막이 생긴 뒤에는 그게 진실이다 (0905)

사용자가 만든 **자막 문구는 보존**하되 cue·words 시각은 검증한다.
0905의 "STT 재전사로 다시 맞추지 않는다"는 원문 대체 금지로 한정한다(2026-10-22).
눌린 cue 의 시각·컷 경계는 §5처럼 실측하며, 무음 판정은 자막이 아닌 §3 교집합이 근거다.

### 문장 끝 보호 — 과거 cue 끝 가드와 현재 오디오 교집합을 구분한다

문장 끝 음절은 원래 조용히 사라져서 **어떤 RMS 임계로도 무음으로 보인다.** 임계를 낮추면
무음이 안 잘리고(§3), 높이면 문장 끝이 잘린다. 임계로는 못 푸는 문제다.

- ❌ **부정확한 어절 시각만으로 말/무음을 확정하지 마라.** CapCut 어절 구간은 타임라인의 **78%** 만 덮고,
  그 '빈틈' 에도 발화가 들어 있다(0905 실측: 빈틈 RMS p90 = **-15 dBFS**).
  마스크로 쓰면 컷 165개 중 **100개가 취소**되고 길이가 되레 늘어난다(5:18 → 6:12).
- **0905의 보수적 cue 끝 가드**: 컷 시작이 직전 cue 끝 + 0.15s 보다 앞이면 그만큼 물렸다.
  0905 실측: 컷의 **17%(27/162)** 가 cue 끝보다 먼저 시작하고 있었고, 보정 후 **0/118**,
  중앙 여유 +0.71s. 되살린 오디오 14.8s.

현재는 **cue 끝만으로 승인하지 않는다**. 어절 시각이 눌리면 실측하고, §3의
auto-editor·VAD·남길 어절∩소리 보호를 모두 적용한다. 과거의 하드 마스크 실패는 이 보호를 생략할 근거가 아니다.

### 카드가 "빠르게" 느껴지면 앵커가 밀린 것이다

컷을 다시 할 때마다 카드 시각을 remap 하면 오차가 쌓인다(0905: 0.5~1.5s 빠름 → 사용자가
"화면이 조금 더 빠른 감" 이라고 했다). **카드 앵커는 자막 문구로 고정한다.**

```python
ANCHOR_TEXT = {"b01": "오늘은 에이에스 사례", ...}   # 사용자 자막 그대로(오탈자 포함)
```

시각으로 잡으면 `card-windows.json` 이 매 빌드마다 remap 결과로 덮여 **다음 실행이 밀린 값을
입력으로 받는다**(실측: 49.07 → 41.23 → 35.91 로 누적). 문구는 안 밀린다.

**화면녹화를 살려두는 구간은 캠 시각으로 따로 못박는다.** 카드 끝을 "다음 카드 시작" 으로만
잡으면 그 구간을 통째로 삼킨다(0905 에서 b14 가 지식DB JSON 구간 46초를 먹었다).

### 컷에 걸린 cue 는 **텍스트도 고친다**

시각만 옮기면 화면엔 지운 말이 남는다 — 지침의 실패 조건("자막만 숨기고 오디오는 남긴다")의
정반대 형태다. 자동자막 `words` 타임코드로 어느 어절이 살아남았는지 확정해 문구를 다시 쓴다.
0905: `이렇게 이렇게 채널` → `이렇게`, `제 이거를 제때` → `이거를 제때`.

> ⚠ **버벅임이 남았는지를 자막 텍스트로 판정하지 마라.** 자막을 리타임만 하면 텍스트는
> 옛말 그대로라 "아직 반복이 있다" 로 잘못 읽힌다. **오디오를 재전사해서** 확인한다
> (0905: 텍스트 기준 3건 남음 → 실제 오디오는 0건).

## 6. 얼굴 PiP 크롭은 자동으로 잡는다

카메라 위치·프레이밍은 촬영마다 다르다. 좌표를 손으로 박지 마라.

```bash
python3 scripts/detect-face.py <캠> --tile --json work/face.json
```

`--tile` 은 OBS 씬처럼 검은 배경에 웹캠 타일만 있는 소스에서 타일 bbox 를 먼저 찾는다.
그 안에서 Haar cascade 로 얼굴을 검출하고 **프레임별 결과의 중앙값**을 쓴다
(한 프레임은 흔들린다). 크롭 변 = 얼굴폭 × 2.15, 눈높이는 위에서 44%.

배율을 1.85 / 눈높이 40% 로 두면 **정수리가 잘린다**(실측). 결과는
`build.py` 가 `work/face.json` 에서 읽는다.

자료화면을 작은 박스에서 전체화면으로 키우자 안 보이던 3곳이 읽히기 시작했다
(브라우저 비밀번호 저장 팝업, 로그인 입력창, 기기인증 계정 칩).

## 8. 레이아웃

**채널 공통 약속은 얼굴의 우하단 원형 배치다. 자료화면 크롭은 장면별로 정한다.**
얼굴을 가림이 적은 자리로 옮기지 말고, 필요한 조작 화면은 아래 contain 배치로 보존한다.
슬라이드는 폭 채움 + 상단 크롭, 코딩·데스크톱·브라우저 조작은 전체 화면(contain, **가로 정중앙**,
메인 캠 alpha 0, Dock 이 보이면 Dock 높이만큼 아래로 밀어내 확대)이다. 전환·검증 절차는 §8-1을 따른다.

| 구역 | 현재 규칙 |
| --- | --- |
| 자료화면 | 슬라이드/조작 구간을 §8-1대로 분리 |
| 얼굴 | ⌀250, 중심 **(1760,920)** — **우하단** 원형 마스크 |
| 자막 | 수평 정중앙 하단(MarginV 34), 78px/여백260. 52px/여백300은 0827 과거값 |
| 자막 배경 | 흰 슬라이드가 있으면 검은 반투명 박스(alpha 0.6, `check_flag \|= 16`). 하단 스크림만으로 대체하지 않는다 |

**과거 사례(0905, 조작 구간 크롭 규칙은 2026-10-22 §8-1로 대체됨).** 상단 250px을 잘라
`crop=3456:1984:0:250` → `19,0 → 1901,1080`, 화면 폭 1670 → 1882px로 키웠다.
당시 VS Code 탭 줄을 잃었지만 글자가 커졌다. 이제 조작 구간은 메뉴·탭도 필요하므로 이 값을 쓰지 않는다.
아래 터미널 입력줄·상태바는 보존한다(0905 상태바: 소스 y 2184~2234, 마지막 50px).
과거 높이 맞춤은 좌우 125px씩 비었고 폭 채움 뒤 여백은 19px이었다. 폭 3456의 16:9 필요
높이는 1944px(2234−1944=290px)이다. 당시 스크림은 `0,820 → 1920,1080` 그라디언트였다.
현재 슬라이드 크롭은 해당 프레임을 확인해 정하고 흰 배경 자막에는 위 박스 규칙을 적용한다.

### 8-1. 코딩·데스크톱 조작 구간은 **전체 화면**이다 (2026-10-22, 1021)

위의 "상단을 잘라 폭을 채운다"는 **슬라이드 구간** 규칙이다. 데스크톱·VS Code·브라우저를 조작하는 구간에서
상단을 자르면 **맥 메뉴바와 앱 메뉴(File·Edit·View…)·탭 줄이 사라진다** — 사용자: "10분부터는 진짜 코딩을 하기
때문에 화면 전체가 나와줘야 메뉴 이런 것도 볼 수가 있어. 지금은 뭔가 줌인 되어 있는 거 같네."

| 구간 | 화면녹화 | 메인 캠 | 얼굴 |
| --- | --- | --- | --- |
| 슬라이드 | 폭 채움(3456 폭 기준 ×1.149) + 상단 크롭 | 보이지 않음(화면이 덮음) | ⌀250 우하단 |
| 조작 — **Dock 보임** | **×(H/(H−Dock))** — Dock 높이만큼 캔버스 아래로 밀어내고 확대, **위 정렬 · 가로 정중앙** (1021: Dock 184px, ×1.0898, 1821×1177, `tx 0`, `ty=(540−1177/2)/540=−0.0898`) | **alpha 0** (소리는 유지) | ⌀250 우하단 (그대로) |
| 조작 — Dock 없음 | **contain ×1.0 — 1671×1080, 가로 정중앙** (`tx 0`) | **alpha 0** | ⌀250 우하단 (그대로) |

- **가로 정중앙이다** — 사용자: "윈도우는 정 중앙에 위치하자 지금은 좌측으로 쏠려서 구도가 이상하네".
  (2026-10-22 처음엔 얼굴 겹침을 줄이려 왼쪽 정렬했다가 구도 문제로 되돌렸다.) 얼굴 원은 우하단 그대로 두고 화면 오른쪽 아래와의 겹침(Dock 확대 시 약 235px)은 감수한다.
- **Dock 은 잘라내지 않고 밀어낸다** — 사용자: "밑에 dock 윈도우 만큼 그 부분 자른다라고 가정하고 확대를 해서 비율을 살짝 맞춰봐".
  세그먼트별 crop 은 재료를 나눠야 해 CapCut 재저장에 취약하니 배율·위치로 Dock 을 캔버스 밖으로 보낸다. 위쪽(메뉴바)은 절대 밀어내지 않는다.
  **Dock 이 보이는 세그먼트에만** 적용한다(전체화면 앱·Dock 숨김 구간은 contain ×1.0). Dock 높이는 원본 프레임의 행별 밝기로 잰다(앱 상태바 끝 ~ 화면 끝).
- **Dock 판정**: 원본 하단 Dock 띠를 1fps 로 뽑아(`fps=1,crop=W:Dock:0:H−Dock,scale=432:23`) **평균 밝기 < 110 이고
  아이콘 줄 가로 변화량 ≥ 10** 이면 Dock 으로 본다. 세그먼트가 덮는 초의 과반이 Dock 이면 Dock 배치, 2초 미만으로 튀는 구간은
  앞 구간을 따른다(깜빡임 방지). ⚠ **기준 프레임과의 상관으로 판정하지 마라** — 앱 아이콘 수가 바뀌면 Dock 폭·위치가 밀려
  눈으로는 같은 Dock 인데 상관이 0.4·0.0 으로 떨어졌다(1021: 3,261초 중 2,600초가 오판 후보). 판정 후 점수 구간별 띠를
  모아 **눈으로** 확인한다. 1021 결과: 코딩 구간 전체(730s~)가 Dock 있음 → 675/675 세그먼트 Dock 확대.
- **캠은 alpha 0** — 띠로 OBS 사각 웹캠 타일이 비쳐 얼굴이 두 번 보인다(0905 의 "백그라운드에 얼굴 클립이 또 있다" 와 같은 문제).
- **전환점은 화면 장면 전환 프레임**으로 잡는다(슬라이드 → 데스크톱: 프레임 평균 밝기 222 → 78 이 시작되는 프레임).
  자막·말 기준이 아니다. 3트랙을 **같은 프레임에서** 분할해 lockstep 을 유지한다(`reapply-captions --mirror-tracks` 가 기대하는 구조).
- 적용 전 ffmpeg 로 두 배치를 한 프레임씩 합성해 비교한다. ⚠ 보조 입력은 `setpts=PTS-STARTPTS` — 빼면 화면녹화가 통째로 안 보인다.
- 구현: `outputs/1021-screen-layout-20261022/layout.py`(분할·캠 alpha), `outputs/1021-dock-zoom-20261022/dock_layout.py`(Dock 판정·정중앙 배치).

x264 는 **홀수 폭/높이를 거부한다**. 스케일 계산 결과가 853 이면 인코더가 안 열린다.

**실패 사례 (0905).** 이 소재는 우측에 채널톡 위젯 입력창과 상담 상세 패널이 영상 내내 있어
얼굴을 **좌하단**으로 옮겼다. 국소적으로는 덜 가리는 게 맞았지만 사용자가 바로
"이전 영상은 우측 하단인데" 로 되돌렸다. **덜 가리는 자리를 편마다 고르는 문제가 아니다.**
그리고 우하단이 가리던 것은 마침 상담 상세 패널의 개인정보였다 — 겹침이 늘 손실인 것도 아니다.

## 8a. 카드 글자는 바닥값을 두고 키운다

**1080p 에서 46px 미만 금지.** 상단 헤더(kicker·섹션 라벨)는 "라벨이니 작게" 로 잡기 쉬운데
모바일에서 그게 제일 먼저 안 읽힌다. 0905 는 kicker 를 24px 로 냈다가 사용자가 **두 번** 지적했다
("글자 자체가 안 보이잖아" → 34px 로 올린 뒤에도 "상단 타이틀이 너무 작다").

| | 처음 | 1차 | 최종 |
| --- | ---: | ---: | ---: |
| kicker | 24 | 34 | **46** |
| 섹션 라벨 | 20 | 34 | **46** |
| 본문 detail | 33 | 38 | **51** |
| 제목(mid) | 74 | 98 | **116** |

**균일 배율로 키우지 마라** — 큰 글자만 커지고 정작 문제인 작은 글자는 덜 커진다.
작은 쪽을 더 올리는 비율을 쓴다:

```python
if px < 60:    new = max(46, round(px * 1.35))
elif px < 110: new = round(px * 1.18)
else:          new = round(px * 1.10)
```

글자를 키우면 여백이 상대적으로 좁아 보이므로 rule 폭·항목 간격도 같이 올린다.
키운 뒤 `npx hyperframes check` 의 layout·contrast 가 0 인지 보고 스냅샷을 눈으로 확인한다.

## 8b. 사용자가 앱에서 편집을 시작하면 **프로젝트를 다시 만들지 마라**

3단계로 넘긴 draft 를 사용자가 CapCut 에서 만지기 시작하면 그때부터 **그 draft 가 진실**이다.
`make-edit-project.py` 는 재료·트랙을 전부 새로 만들므로 그 편집이 통째로 날아간다.

**md5·재료 수만으로 사용자 편집이라 판정하지 않는다.** 앱은 열기만 해도 video 재료를
세그먼트 수만큼 복제하고 자막 시각을 ±1프레임 스냅한다(1021). 저장 전/후 구조·텍스트·
source/target diff 로 실제 편집을 구분하고 현재 draft 를 새 기준선으로 삼는다.
0905 아래 사례는 duration·컷 구조가 함께 바뀐 사용자 편집이다:

| | 우리 출력 | 사용자 편집 후 |
| --- | --- | --- |
| 트랙 세그먼트 | 1 / 1 / 25 / 1 | **27 / 25 / 38 / 25** |
| videos 재료 | 4 | **115** |
| 마스크 | 1 | **25** |
| duration | 316.17s | **275.53s** (41초를 잘랐다) |

그 상태에서 할 수 있는 것은 **제자리 수정**뿐이다:

- **자막 크기·스타일** — 재료의 `content.styles[*].size` 와 `font_size` 를 **둘 다** 고친다.
  하나만 고치면 앱에서 다르게 렌더된다. (`caption_size.py`)
- **소재 화질/디자인** — 같은 **길이·해상도**로 다시 구워 `assets/<파일>` 을 덮어쓴다.
  타임라인은 그대로 두고 그림만 바뀐다. 길이가 다르면 세그먼트의 source range 가 깨지므로
  바꾸기 전에 `ffprobe` 로 길이를 맞춰 본다.
- 무엇을 하든 **앱 종료를 확인하고** 백업한다. 실제 프로젝트의 미러를 확인해 모두 동기화한다
  (위 사례는 6개). 앱이 열려 있으면 절대 쓰지 않는다. 검증용 open→close는 기본 실행하지 않는다.

## 9. 후편집용 프로젝트는 "레이어는 나누고 세그먼트는 합친다"

가편집 draft(3트랙 × 수백 세그먼트)는 손으로 못 자른다. 전부 한 클립으로 구우면
자료화면을 손볼 수 없다. **레이어별 플랫 클립을 트랙당 1세그먼트로** 올리되
슬라이드/조작 배치 전환은 §8-1대로 3트랙을 같은 프레임에서 분할한다.

| 트랙 | 클립 | 배율 / 좌표 | 오디오 |
| --- | --- | --- | --- |
| 메인 (flag 0) | `edit-base.mp4` — **배경색 단색** 1920×1080 | 1.0 / (0,0) | **O** (마스터링됨) |
| 오버레이 1 | `edit-screen.mp4` (1670×1080은 0827 예시) | 슬라이드/조작 구간별 §8-1 적용 | X |
| 오버레이 2 | `edit-face.mp4` 250×250 | 0.2315 / (0.833, -0.704) | X |

**얼굴에는 CapCut 원형 마스크를 걸어 둔다.** 최종 렌더는 ffmpeg 이 알파 마스크로 오리지만,
**사용자가 CapCut 에서 보는 것도 원형이어야 한다** — 사각으로 두면 후편집 중 계속 사각으로 보인다.

```bash
# make-edit-project 는 재료를 전부 새로 만들므로 **프로젝트를 만든 뒤에** 건다
node dist/index.js mask <프로젝트> <얼굴 세그먼트 id> circle --size 1.0
```

⚠ **마스크 `config.width`/`height` 는 캔버스가 아니라 *소재 자신의* 가로·세로 대비 분수다.**
`--size 1.0` 이면 소재 전체를 덮는다. **레포에서 빌드한 `dist/index.js` 를 사용한다.**
전역 `capcut` 설치본은 아래 수정 전 버전이라 정사각 소재를 타원으로 만든다.

**16:9 소재에서는 이 구분이 안 드러난다** — 캔버스와 종횡비가 같아 두 해석이 같은 값을 낸다.
정사각 소재에서만 갈린다: 250×250 얼굴 클립에 캔버스 기준으로 계산하면
`width 0.5625 / height 1.0` → **141×250 px 타원**이 된다. 실제로 그렇게 나갔다.

`capcut-cli` 의 `addMask` 가 캔버스로 나누고 있어서 고쳤다(`src/decorators.ts`,
회귀 테스트 `test/decorators.test.mjs`). **0819 draft 로 교차검증**: 1280×720 소재에
손으로 그린 원이 `w 0.4120 / h 0.7357` → 소재 픽셀로 527×530, 즉 원이다.

배율은 **contain 기준**이다 — 250×250 정사각은 1920×1080 캔버스에 1080×1080 으로
들어가므로 ⌀250 을 만들려면 `250/1080`. 좌표는 `tx=(cx-960)/960`, `ty=(540-cy)/540`.

**메인 트랙에 캠 영상을 올리지 마라 — 배경색 + 오디오만 둔다.**
캠 원본이 OBS 씬이면 프레임 대부분이 검정이고 우하단에 **사각 웹캠 타일**이 박혀 있다.
그걸 메인에 올리면 ① 마스킹 안 된 얼굴이 배경에 **한 번 더** 깔리고 ② 자료화면이 못 덮는
좌우 띠(0905: 19px)로 새어 나온다. 0905 에서 사용자가 "백그라운드에 얼굴 클립이 또 있다,
그냥 마스킹만 해라" 고 지적한 지점이다.

**얼굴은 오버레이 한 장이 전담한다** — `edit-face.mp4` + CapCut 원형 마스크.
메인은 자를 기준선(오디오)과 배경 역할만 한다.

```bash
ffmpeg -f lavfi -i color=c=0x0f1117:s=1920x1080:r=30 -i work/head.mkv \
  -map 0:v -map 1:a -af "<마스터링>" -frames:v <N> edit-base.mp4
```

새 프로젝트는 CapCut 기본 draft root 에 만들고 `root_meta_info.json` 에 등록한다.
소재를 `assets/` 로 복사하고 draft_info·draft_content·draft_meta·root_meta 의 미디어 경로가
프로젝트 내부 절대경로인지 검증한다(TCC). 얼굴은 **캠에서 별도 크롭한 클립 + CapCut 원형 마스크**다.

사용자는 **메인 트랙에서만** 자른다. 오버레이와 자막은
`reapply-captions.py --mirror-tracks` 가 같은 조각으로 다시 만든다. 장면별 배치(§8-1)도 조각마다
원래 세그먼트의 배치·마스크를 물려받아 유지된다(2026-10-22 수정, 1021 draft 복사본으로 검증: 배치 2종 유지·
전환점 이후 폭 채움 0·얼굴 마스크 900/900).
